# Acceptance criteria — FitFindr

Five criteria that say what "working" means for this agent, written in unit 3
**before** any results existed.

An acceptance criterion names a target: a number, a count, a rate, or something
a person could plainly observe. *"The agent handles errors"* is an opinion.
*"When search returns nothing, the agent stops before calling the second tool,
in 5 of 5 tries"* is a criterion.

Under each one, write a sentence or two on **why that target** and not a
stricter one. A reason that says something about your tools, your loop, or the
data earns credit; *"80% seemed reasonable"* does not.

> Missing your own targets next unit costs you nothing. Setting a target so
> easy you can't miss it does.

**Two are written for you. You write three.**

---

## 1. A matching query completes all three tools

Given a query that matches at least one listing, the agent completes all three
tool calls and returns a fit card — in at least 4 of 5 tries.

**Why this target:**
I chose 4 of 5 because `search_listings` uses deterministic keyword overlap,
so an unfamiliar phrasing may not match the words in the listing data even
when a relevant item exists. The later outfit and fit-card steps also use the
model, whose wording and service availability can vary between runs.

---

## 2. An impossible query stops before the second tool

Given a query that matches no listings, the agent stops before calling
`suggest_outfit` and returns a message naming what to change — 5 of 5 tries.

**Why this target:**
I chose 5 of 5 because this is a deterministic branch in the planning loop.
Once `search_listings` returns an empty list, the agent can detect that result
directly, store a useful message, and return before either model-backed tool is
called.

---

## 3. The selected item stays the same across session state

Given a query that returns at least one listing, the item stored in `session["selected_item"]` is the same listing passed into `suggest_outfit` — in 5 of 5 tries.

**Why this target:**
I chose 5 of 5 because the agent explicitly saves the chosen listing in session state before calling `suggest_outfit`. Since this transfer is handled directly by the planning loop rather than generated by the model, the same item should be passed every time.

---

## 4. The fit card includes useful information about the selected item

Given a successful search and outfit suggestion, the final fit card names the selected item and includes at least one styling detail from the outfit suggestion — in at least 4 of 5 tries.

**Why this target:**
I chose 4 of 5 because the final fit card is model-generated, so the wording and which styling details it emphasizes can vary. However, because the model receives both the selected listing and the outfit suggestion, I expect it to preserve the selected item and at least one useful styling detail in most runs.

---

## 5. An empty wardrobe does not cause the agent to fail

Given an empty wardrobe, `suggest_outfit` returns at least one general styling recommendation and does not raise an error — in 5 of 5 tries.

**Why this target:**
I chose 5 of 5 because the empty wardrobe is a predictable input that `suggest_outfit` can detect directly. It does not depend on finding or selecting wardrobe items, so the tool should consistently fall back to general styling advice instead of crashing or returning an unusable result.
